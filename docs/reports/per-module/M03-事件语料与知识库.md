# 板块 3 · 事件语料与知识库

> 边界：`engines/event-corpus.ts`（522 行）+ `event-graph-builder.ts` + `lib/graph/*`（entity-extractor / graph-store）+ `personal-graph-builder.ts`；API：`/api/events`、`/api/graph/[userId]`；数据：`data/event-corpus.json`。

## 一、流程合理性 / 走通性 / 人类使用习惯

**流程链路**：`event-corpus.json`（55 条已解决事件）→ `event-graph-builder`：GLM-4 抽取实体/关系 → 关键词模板识别利益相关方 → 注入"流年"外部力 → 去重 → `graph-store` 建图 → 社区划分阵营 → 生成摘要。理念正确："事件推演用现代情报、古典 substrate 不参与事件判定"（边界清晰，避免伪科学）。

**走通性 / 风险**：
- **语料规模过小**：55 条（prior 报告建议 55→150），且自动回写仅在 `corpusId` 命中时发生——自由文本事件结局未知，闭环覆盖极窄。
- **利益相关方识别是关键词模板**（8 类硬编码：创业者/投资方/政策方…），脆：**漏掉语义 nuanced 主体**（如"开源社区""监管科技"），且中英文混输时模板命中率下降。
- `entity-extractor` 依赖 GLM-4 外部调用，离线/限流即降级；图持久化 + 中心度 + 社区检测本身实现正确。

**人类使用习惯**：把"一个事件"画成多方博弈图谱是**强差异化、直觉友好**的可视化；但模板标签可能张冠李戴，用户看到"阵营1/阵营2"无名无义，需可编辑/可命名。

**结论**：理念 9/10，规模 2/10，抽取质量 4/10，可视化价值 7/10。

## 二、市场竞品与需求比较

| 参照 | 定位 | 关系 |
|---|---|---|
| Metaculus 题库 / GDELT | 事件库 / 全球事件流 | OracleMind 语料极小，GDELT 可提供历史真事件回填 |
| WikiData / EventRegistry | 知识图谱 / 事件抽取 | 抽取与 KG 能力可借鉴 |
| 通用 KG 产品 | 企业知识图谱 | OracleMind"预测+图谱"组合全球无人做 |

**需求**：预测类产品用户要"这事和谁有关、谁受益"的可解释图谱；当前模板法不足以支撑可信解释，且语料太小导致校准闭环几乎不触发。

## 三、最新开源技术融合机会

- **LlamaIndex + GraphRAG（NebulaGraph/Neo4j）**：把古典规则 + 现代情报建成可检索知识图谱，RAG 回答多跳"为什么"。
- **GLiNER / InstructIE / OpenSPG（蚂蚁开源）**：LLM 事件/实体抽取，替换关键词模板，支持中英文与细粒度主体。
- **GDELT / EventRegistry**：实时事件流 + 历史已解决事件库，可直接回填 `event-corpus` 到 150+ 条真事件，打通自动回写闭环。
- **Ant OpenSPG**：规则图谱，结构化"格局/用神"等命理规则供 GoT 共识。

## 四、单板块提升方案

- **P0-①**：用 GDELT 历史已解决事件把语料从 55 → 150+，让 `event-outcome-ledger` 自动回写真正高频触发。
- **P0-②**：用 GLiNER/InstructIE 替换关键词模板做利益相关方抽取，支持中英文与 nuanced 主体。
- **P1-①**：图可视化支持用户编辑/命名阵营，导出分享。
- **P1-②**：接入 GraphRAG，使古典解读与现代情报都能"引用图谱节点"而非空谈。
- **P2**：图谱节点与前瞻性注册联动，形成"预测时可验证、结局时可对账"的完整证据链。

**板块健康度评分（0–5）**：理念 5 · 规模 2 · 抽取质量 2 · 可视化价值 4 · 开源可融合 4 → **综合 3.4**
