1. **样本量**：54 条。CI95 宽度约 0.06，但**分域后每域仅 5–15 条**，science 域 Brier 0.220 / 方向 0.60 明显拖后腿。
2. **非前瞻性**：54 条是**历史回测语料**（openDate 2022–2024），不是"注册在先、结算在后"的前瞻性预测。**没有前瞻性注册，就无法对抗"事后叙事"指控**——而学术界最看重的恰恰是这一点。
3. **融合自曝**：`prediction-engine.ts:97` 注释承认终值 = `(现代共识 + 古典共识)/2`，**蒙特卡洛权重 0**。而对外宣称"10,000 次蒙特卡洛 + 10 Agent 共识"。这是**科学诚信层面的自曝问题**，必须二选一：要么真正接线，要么停止宣称。

### 4.3 科学先进性的诚实结论

- **在"校准"这条线上，OracleMind 比 95% 的预测产品更专业**：它有共形预测的覆盖率保证、有零数据安全的收缩层、有诚实降级。这不是营销话术，是真实代码。
- **在"预测精度"这条线上，它处于"与顶级 AI 同量级、但样本不足以宣称优于基线"的状态**。系统自己知道这一点并明确说出来（`canClaimSkill:false`）——**这是全项目最值得保留的品质**。
- **最大的科学缺口不是算法，是"测量"**：没有前瞻性注册、没有活体记分板、没有足够样本。arXiv 2608.23058（2026-08 LLM 预测智能体综述）把"测量"列为该领域核心局限，而 OracleMind 天然具备补上它的基础设施（JobRun 账本 + historical-backtest）。

### 6.3 技术深度的真实评价（分层）

**深度真实的部分（值得保留）：**
- `conformal-prediction.ts`：真实的 Split-Conformal 实现，含 `ceil((n+1)·q)` 有限样本修正、n<3 诚实降级、明确标注"覆盖率保证是边际的（对单个新样本）而非条件性的"——**这是有统计素养的代码**。
- `calibration.ts`：经验贝叶斯收缩 `shrink = n/(n+K)`，零数据收缩至基率 0.5，并输出 `recommendedConfidenceCap` 用于 prompt 注入——**设计原则正确**。
- `prediction-engine.ts`：确定性随机（参数 hash 做种子，同输入同输出）替代 `Math.random`——**可复现性做对了**。
- `forecast-guard.ts` / `retrieval-signature.ts`：分位数、可信区间、跨变量一致性、检索签名一致性——**诚实护栏体系完整**。

**深度存疑的部分：**
- **40 个引擎模块中，多数是 LLM 编排**（agent-factory 670 行、react-reasoner 576 行、modern-deep-analysis 2766 行）。它们提供"看起来专业"的结构，但**不产生可测量的精度增益**（否则 Brier 早就更好）。
- **融合层是加权平均**，而非贝叶斯更新——**这是科学深度上的实质落后**（详见 §七）。
- **`intel-adopt` 假闭环**：237 条 AgentExperience / **0 insight**，且主引擎不消费。**"自演进"目前是写库自嗨。**

### 7.2 融合点一：用贝叶斯更新替换加权平均（**方法论级升级**）

**问题**：现有融合是加权平均（现代 0.5 + 古典 0.5 + 蒙特卡洛 0）——**情报一多就被稀释，且不可解释，且与"三层加权"宣称矛盾**。

**推荐：贝叶斯更新框架**

```
先验 P(H)              ← 引擎基准概率（古典 substrate + 多 Agent 共识）
   ↓
+ 情报证据 E₁ … Eₙ     ← 每条带似然比 LR = P(E|H) / P(E|¬H)
   ↓
后验 P(H | E₁…Eₙ)      ← 最终输出概率
```

**为什么这是正确的方法：**
1. **天然处理"新信息如何改变判断"**——这正是预测的本质。
2. **可解释**：能算出每条情报贡献了多少概率变化，可展示给用户（**别人做不到**）。
3. **与「概率演化追踪」玩法完全一致**——玩家看到的信念更新曲线，底层就是贝叶斯更新。
4. **自动抑制过度反应**：单一证据的似然比有限，不会因一条传闻就翻转。
5. **优雅统一**：情报层 + 概率演化玩法 + 商业预测，三者共享同一底层。

**证据权重必须做四件事（否则退化为噪声）**：源可信度加权 / 时效性衰减 / 相关性过滤 / **独立性检查**（同一信息的多源只算一次——这是最常见的错误，会导致概率被虚假推高）。

**风险边界**：🔴 **幻觉情报**（LLM 编造信号）→ **强制溯源**：每条情报必须有 URL + 时间戳；**无法溯源的证据权重 = 0**（契合 CORE-GOALS 已有"零幻觉强制"原则）。

### 7.3 融合点二：L3 事件 × 数值融合（**真正的创新点，全球无人做**）

**三层路线：**

| 层 | 内容 | 现状 | 竞争格局 |
|---|---|---|---|
| **L1 商业事件预测** | 竞品会不会降价？法规会不会通过？供应商会不会断供？并购会不会成？ | 可做，**几乎无人竞争** | Gartner 做定性（无概率无记分板）；预测市场只做公共事件 |
| **L2 校准增强数值预测** | 客户历史序列 → 开源 TSFM → **共形层输出有覆盖率数学保证的区间**（不是模型自己拍的方差） | 可做，成本极低（不训练只后处理） | 接 TSFM 即可 |
| **L3 事件 × 数值融合** | 把离散事件概率注入数值预测 | **全球无人做**，且完美复用现有资产 | 见下表 |

**L3 示例：**

├─ 供应商 A 不断供   82%  → 失败则 -18%

条件情景：全部顺利 52%→13,500 ｜ 竞品降价 24%→11,900
         供应商断供 15%→9,800 ｜ 最坏组合 2%→7,200

### 7.4 融合点三：情报层（三轨统一的新内核组件）

```
        ┌── 情报层 Intelligence Layer ────────────────┐
        │  实时信号 · 技术系数 · 竞争态势 · 需求趋势   │
        └────────────────┬───────────────────────────┘
                         ↓ 贝叶斯更新
   事件轨  ←── 内核层（多Agent共识 + 共形预测 + 校准）──→  商业轨
                         ↑
                      个人轨
```

| 轨道 | 现在缺什么 | 情报层补什么 |
|---|---|---|
| 事件轨 | 静态语料，无实时信息 | 实时新闻、政策动向、专家观点、市场信号 |
| 个人轨 | 只有生辰 → 倾向场，无外部情境 | 行业景气、地域经济、时机窗口 |
| 商业轨 | 完全没有 | 竞争情报、技术成熟度、需求信号 |

**💡 对个人轨的特殊价值（同时解决产品力与合规）**：
- ❌ 旧 framing："从你的生辰推出你的命运" → 不可验证、合规风险高
- ✅ 新 framing：**"在给定的外部环境下的概率倾向"** = 倾向场（内在）× 情报层（外在情境）

> 例：同一个人在行业上行期与下行期，"换工作成功"的概率倾向显然不同。把行业景气度、地域经济、时机窗口纳入后，输出从"命定"变成**"内外因共同作用下的概率"**。
> → **这让个人轨更可信、更有用，且完全避开算命指控**——因为它明确纳入外部客观因素。

**商业预测五要素模型（量化方法 + 硬度）：**

| 要素 | 量化方法 | 数据源 | 硬度 |
|---|---|---|---|
| **① 技术发展系数** | **莱特定律**（成本随累计产量翻倍下降固定比例，Santa Fe 性能曲线库有 **155 项技术**实证）、S 曲线渗透率、TRL | 论文/专利增速、Santa Fe 库、融资事件、成本数据 | ⭐⭐⭐ **最硬** |
| **② 竞争态势** | 竞品动作概率（**OracleMind 强项**）、招聘信号（招什么岗位 = 战略暴露）、专利布局、定价变动 | 招聘站、专利库、SEC filing | ⭐⭐ |
| **③ 需求趋势** | 搜索趋势、渗透率曲线、价格弹性、替代品交叉弹性 | Google Trends、行业报告、库存数据 | ⭐⭐ |
| **④ 监管与政策** | 立法进程概率、监管表态、合规时点 | 政府公告、立法追踪 | ⭐⭐（事件轨可复用） |
| **⑤ 宏观与资本** | 利率路径、融资环境、行业资本流动 | 宏观数据、融资数据库 | ⭐⭐ |

> **竞争情报定位**：SignalMark / Signal Six / Electa / KSPIONAGE 等已在做融资、招聘激增、产品发布、专利、定价的信号**监控**。
> **但它们是"监控"不是"预测"。** OracleMind 应做它们的下游：**情报告诉你"发生了什么"，OracleMind 告诉你"这意味着某件事发生的概率是多少"**。这是明确的生态位，而非竞争。

**核心产品：Certified Probability（带校准证书的概率）**

// POST /api/forecast → Response  ← ✅ 已上线

## 十一、结论（不附和）

1. **这个项目不是"缺功能"。** 85,562 行代码、40 引擎模块、共形预测、校准层、16 条自动化链、MCP/A2A/OpenAPI 全齐——**工程与科学内核的密度已经超过绝大多数同阶段产品**。继续堆功能是负收益。

2. **它的科学内核是真的，而且比它自己以为的更值钱。** Brier 0.136 / 方向 83.3% 落在预测市场区间；共形预测的覆盖率保证是**绝大多数竞品没有的**；系统主动声明 `canClaimSkill:false` 是**行业罕见的诚实**。这三样加起来，构成了一个**无人占领的定位：可验证的概率层**。

3. **但它最硬的资产保护错了对象，最弱的环节却承担了门面。** 专利保护的是无关的化学优化方法；古典 substrate 实际只有 2/5；营销门面长期放在不可自证的个人轨上。**该保护的没保护，该放大的没放大。**

4. **真正的技术壁垒尚未形成——但图纸已经画好了。** 唯一"时间不可压缩"的壁垒是**累积的前瞻性注册数据集**；唯一"赢者通吃"的壁垒是**"带校准证书的概率"这一品类标准**。二者共用同一套基础设施，而**这套基础设施（哈希封存 + JobRun 账本 + 校准层）你已经有了**。

5. **如果只能做一件事**：
   > **接线 arena 提交 → `prisma.prediction.create`。**
   > schema 已就位（`probability` / `outcome` / `resolvedAt`），业务侧 0 消费。不做这条，"概率演化追踪"、"个人战绩档案"、"长期校准飞轮"全是空谈。完成成本低、风险低、杠杆最高。

   **第二件事（并行）**：**修 `/tuivan` 红线泄漏 + 前瞻性注册接线** —— 前者保护支付通道与品牌，后者是学术/媒体信任的唯一入口。

6. **做完 P0+P1，项目的形态应该是**：一个公开记分板的概率层——首页挂着 Brier 曲线和 150+ 已解决事件，用户来追踪事件、看自己的校准成长曲线、买 $4.99 的深度解读，开发者的 Agent 通过 MCP 付费调用它的概率场。**这与今天的"AI-Powered Life Forecasts"是两个物种，而前者才有护城河。**

### A.2 新发现（断链 #6）：逐次「校准证书」读静态语料，不读实时飞轮

这是本次复扫最重要的**新增断链**，且上次报告未覆盖：

`src/lib/science-layer.ts` 的 `collectCalibrationPairs()`（L47-58）从**静态 `EVENT_CORPUS`**（JSON 文件）收集校准对；而该文件"当前不携带 `predictedProbability/actualOutcome` 字段，故 sampleSize 通常为 0"（源码注释第 49 行原文）。于是每次预测的 `final.scienceLayer.calibration` 永远走"收缩到 0.5、置信上限 ≈ 0.5、保形全区间"的诚实降级分支。

**后果**：即便 arena 上线、飞轮把真实样本灌进 `db.predictionFeedback`，**用户在前端看到的"逐次校准证书"仍显示"无校准样本"**——因为证书的数据源是错的表。Agent 提示层（走 `getHistoricalAccuracyContext` → `db.predictionFeedback`）会被喂到，但**用户可见的证书卡片不会**。两条校准消费路径数据源不一致，是典型"半接通"。

**修复（低成本）**：把 `collectCalibrationPairs()` 重定向为查询 `db.predictionFeedback` 的 verified 行（与 `getHistoricalAccuracyContext` 同源），转为 `ScorePair[]` 喂给现有 `calibrateProbability` + `splitConformalPrediction`。这样 arena 一上线，证书即自动从"全区间降级"转为"真实经验校准"。建议列为 **P0-1.5**，优先级高于原 P0-4（扩产），因为它让已有基础设施立刻产生可见价值。

### A.3 附带发现：概率演化底座已就位，但 arena 尚未消费

`prediction-feedback.ts` 已新增 `upsertPredictionRecord()` + `resolvePredictionRecord()`，落 `db.prediction` 表本体（schema 已加字段，对应上次报告 0-3 底座）。该写入入口的幂等键是 `(userId, question)`，正是"1-1 概率演化追踪"所需的干净时间序列。但截至本次复扫，**arena 仍只写 `db.predictionFeedback` + ServiceMeta KV，未调用 `upsertPredictionRecord`**。故"个人概率演化曲线 / 校准成长曲线"（上次 P1-2）的数据底座虽在，仍未被填充。属中优先级接线项。
