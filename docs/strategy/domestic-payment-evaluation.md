# 国内支付渠道（虎皮椒 / 微信·支付宝）接入评估

> 🚫 **决策（2026-08-12）：不推进。** 用户决定聚焦海外、保持 PayPal 单一支付闭环，国内支付暂不接入。下文仅留档供将来参考。
>
> 结论先行：**条件性可做，唯一硬门禁 = 商户类目必须中性（非命理）。类目过关就接，不过关绝对不接。**

## 一、技术可行性 —— 高，低风险

虎皮椒是微信+支付宝聚合支付，标准模式：后端下单 → 返回支付二维码/链接 → 用户扫码 → 异步 `notify` 回调 → 验签 → 开通权限。

直接镜像现有 PayPal 集成（已生产 19/19 验证）：

| PayPal 现有 | 虎皮椒对应 | 说明 |
|---|---|---|
| `PAYPAL_ITEMS`（USD SKU 表） | `HUPIJIAO_ITEMS`（RMB SKU 表） | 新增，价格按汇率折算 |
| `buildCheckoutUrl()` | `createOrder()` | 返回微信/支付宝支付链接或二维码 |
| `verifyIpn()` | `verifyNotify()` | 异步回调验签（虎皮椒用 md5/签名） |
| `applyPaypalGrant()`（已抽共享） | 直接复用 | 开通逻辑零分叉 |
| checkout / ipn 两个路由 | checkout / notify 两个路由 | 新增 |
| pricing 页按钮 | pricing 页加 "Pay with WeChat / Alipay" | 英文 UI 不改 |

改动量：约 2 个新文件 + 2 个路由 + pricing 按钮 + SKU 表加 RMB 列。一个会话可上线，并用受控 self-test 跑通开通+幂等（同 PayPal 那套验证）。

**双币种**：`CreditTransaction` 已有 amount 字段，需补 `currency` 维度做对账。低成本。

## 二、合规风险 —— 唯一否决点（必须你先确认）

项目硬性红线：对外禁 **八字/天干/命理/算命/divination/horoscope**，统一用"古代推演/概率场/Resonance"。

微信支付、支付宝、虎皮椒都对**商户经营类目**敏感。若类目被归为"占卜/算命/风水/命理咨询"，**资金可能被冻结、商户被封**——这正是之前 Creem 审核被拒（疑类目风控）的根因。

你已开通虎皮椒，说明当时填了某个类目。这一步**必须由你确认**：

- ✅ 类目为中性（如"软件/信息服务""会员订阅 SaaS""网站服务""信息技术"）→ 接入安全。
- ❌ 类目偏命理（如"占卜""算命""风水""运势"）→ **不要接**；或先把虎皮椒商户类目改成中性再接。

> 即使用中性类目，对外文案也要继续用"probability field / ancient derivation frameworks"，绝不在支付/商品名出现 fortune/divination/命理词（PayPal 商品名已是英文中性，照此即可）。

## 三、产品定位 —— 低冲突（加法，非重构）

你明确：英文 UI 不改、只是支持国内用户。这是**加法**：英文界面 + 一个 "Pay with WeChat / Alipay" 按钮，国内用户扫码付 RMB，海外用户继续 PayPal USD。无定位冲突。

隐性张力（运营层，非技术阻塞）：国内用户大概率对英文"probability field"叙事转化低。你说"只是支持而已"，可接受。

## 四、成本 / 收益 —— 倾向做

- 虎皮椒已开通（沉没成本已付），增量仅集成代码，低。
- 国内用户若无 PayPal/双币卡，现在**完全无法付费** → 真实转化漏损，接了能补上。
- **不提升准确率**：核心瓶颈是反馈数据（0 outcome），不是支付。接虎皮椒只拓宽付费入口。

## 五、税务 / 运营提醒

- RMB 入账到**个人**微信/支付宝：有提现手续费 + 个税申报义务，且个人商户有年交易限额。
- 建议走**个体工商户 / 企业**账户更稳（也呼应之前"大陆主体收外币"的讨论）。
- 双币种对账：月报分开 USD/PayPal 与 RMB/虎皮椒。
