# OracleMind 产品形态设计提案：概率层 + 游戏化 + 协议化

> 日期：2026-10-10 ｜ 类型：**设计提案（待 owner 讨论确认）**，非定案
> 触发：owner 澄清 —— *"用游戏的思路去设计项目，并不是把项目做成游戏。要的是可玩性、更多预测玩法、更多数据样本、更多互动性；预测本身这个思路没变。盈利性降低后空间更大，比如把预测做成 MCP，接入任何场景。"*
> 本文修正上一版报告（10-09）中"转型为预测游戏"的表述偏差。

---

## 一、先校准理解：你要的不是"游戏"，是三件事

| 你的原话 | 我的理解 | 与"做成游戏"的区别 |
|---|---|---|
| "用游戏的思路去设计" | **游戏化（Gamification）**：用游戏设计手法提升产品的可玩性与留存 | 游戏 = 产品本体是娱乐；游戏化 = 产品本体不变，外面长一层参与机制 |
| "预测本身这个思路没变" | **内核不变**：事件轨可验证 + 个人轨倾向场，双轨结构保留 | 不推翻 CORE-GOALS 的双轨定位 |
| "更多预测玩法" | **玩法维度扩展**：预测的对象 / 形式 / 互动方式都要变多 | 不是加小游戏，是让"预测"这件事本身长出更多形态 |
| "更多数据样本" | **样本飞轮**：可玩性必须反过来喂养校准数据 | 好玩只是手段，**样本增长才是目的** |
| "互动性和成瘾性" | **参与机制设计**，但要守住 Precision Over Hype | 良性成瘾 ≠ 黑暗模式 |
| "做成 MCP，接入任何场景" | **协议化 / 可携带**：预测成为一种可被任何应用调用的能力 | 这是**定位升级**，不是功能增加 |

> **一句话概括你的想法**：*让预测变成一种**可携带的能力**——它在你的产品里好玩，在别人的产品里可用，而每一次被使用都在让它变准。*

## 二、重新定位：从"预测网站"到「概率层 + 记分板」

我建议把定位从"概率场实验室"升级为：

> **OracleMind = 概率层（Probability Layer）+ 记分板（Scoreboard）**
> 类比：Stripe = 支付层，Twilio = 通信层，**OracleMind = 概率层**。

### 三层架构

```
┌──────────────────────────────────────────────────────────┐
│  玩法层 Play Layer                    负责「有趣」        │
│  事件预测 / 个人遗嘱 / 元预测 / 条件链 / AI 辩论 / 对决    │
│  → 产出：用户参与、样本、社区                              │
├──────────────────────────────────────────────────────────┤
│  协议层 Protocol Layer                负责「无处不在」    │
│  MCP / A2A / OpenAPI / Widget / 浏览器插件 / Discord Bot  │
│  → 产出：分发、生态、跨场景样本                            │
├──────────────────────────────────────────────────────────┤
│  内核层 Kernel Layer                  负责「可信」        │
│  10 Agent 共识 / 共形预测 / 校准层 / Brier / 推理图谱      │
│  → 产出：带校准证书的概率                                  │
└──────────────────────────────────────────────────────────┘
```

**三层互相喂养，这是飞轮：**

```
玩法层产生样本 ──→ 内核层变准 ──→ 协议层有价值 ──→ 更多场景接入
     ↑                                                    │
     └──────────────── 跨场景回流更多样本 ←─────────────────┘
```

> **为什么必须三层**：只做玩法层 = 又一个 Manifold；只做协议层 = 没有灵魂的 API；只做内核层 = 就是现状（Brier 0.136 躺在数据库里没人看见）。**三层缺一，飞轮不转。**

## 三、玩法矩阵：预测的设计空间（3 × 6 × 5 = 90 种组合）

你现在只占了这一格：**公共事件 × 二元概率 × 独处**。

### 维度 1：预测「什么」（对象）

| 对象 | 说明 | 现状 | 想象力 |
|---|---|---|---|
| 公共事件 | 会不会发生 | ✅ 有 | 继续扩产 |
| **个人事件** | 我自己的事（预测遗嘱） | 🔶 有轨无产品 | 情感钩子最强，且完全合规 |
| **他人行为** | 朋友/公众人物会怎么做 | ❌ | 社交张力极强 |
| **集体判断（元预测）** | "人群会预测多少？" | 🔶 arena 已有 `probability` 字段可复用 | 二阶思维，智识快感 |
| **AI 的行为** | "这个 AI 会怎么回答？" | ❌ | 2026 最应景的玩法，且数据天然可得 |
| **自己的过去** | "三个月前的我，猜对了吗？" | ❌ | 时间胶囊式回顾 |

### 维度 2：怎么「预测」（形式）

| 形式 | 说明 | 现状 | 价值 |
|---|---|---|---|
| 二元 | 是/否 | ✅ | 基础 |
| 概率 | 0-100% 滑块 | ✅ arena | 基础 |
| **数值区间** | "通胀会落在 2.3–3.1%" | ❌ | 更考验校准，数据更丰富 |
| **排序** | "这 5 家公司谁先发布？" | ❌ | 好玩且易产生互动 |
| **时点** | "什么时候发生？" | ❌ | 天然产生时间序列数据 |
| **条件链** | "如果 A 发生，B 的概率是多少？" | 🔶 有图引擎 | 训练结构化推理 |

### 维度 3：和谁「玩」（互动）

| 模式 | 说明 | 现状 |
|---|---|---|
| 独处 | 自己预测自己看 | ✅ |
| **vs AI** | 与引擎对赌 | 🔶 `engineIndex` 已算，未产品化 |
| **1v1 对决** | 两人相反预测，只有一方赢 | ❌ |
| **组队** | 聚合预测（文献证明团队 > 个人） | ❌ |
| **群体** | 同一事件的群体分布 | 🔶 arena 有人群值 |

> **关键结论**：你不缺引擎，你缺的是**把这 90 格里的十几格产品化**。
> 建议首批只挑 **5–6 格**做深，而不是铺开。选型原则见 §四。

## 四、10 个具体玩法创意（按投入产出排序，标注可复用资产）

> 筛选原则：① 能产生样本 ② 能复用现有代码 ③ 能形成差异化 ④ 不触碰合规红线

| # | 玩法 | 一句话 | 可复用资产 | 难度 | 价值 |
|---|---|---|---|---|---|
| **1** | **概率演化追踪** | 同一事件在 T-30/T-7/T-1 三次预测，画出你的信念更新曲线 | `Prediction` 表需加 `probability` 字段（**目前没有**） | 中 | ⭐⭐⭐⭐⭐ |
| **2** | **嵌入式预测** | 在别人的场景里预测（浏览器插件 / Discord Bot / Notion） | MCP(1.3KB) + OpenAPI(5.7KB) + embed.js(2KB) 已有骨架 | 中 | ⭐⭐⭐⭐⭐ |
| **3** | **预测解剖 Autopsy** | 结算后不止给分，指出你推理链的哪一步错了 | `causal-reasoning`(14.8KB) + `reflection-engine`(12.4KB) | 中 | ⭐⭐⭐⭐⭐ |
| **4** | **个人预测遗嘱** | 对自己的事下预测，哈希封存，到期揭晓复盘 | `probabilityHash`（10-09 刚落地） | 低 | ⭐⭐⭐⭐ |
| **5** | **条件预测链** | "如果 A，那么 B" 形成推理图谱 | `scenario-synthesizer`(20.8KB) + `GraphNode/Edge` | 中 | ⭐⭐⭐⭐ |
| **6** | **AI 陪练辩论** | 让 AI 扮演反对者与你辩论，辩完再预测 | `agent-factory` + `self-consistency` | 中 | ⭐⭐⭐⭐ |
| **7** | **年度回顾 Wrapped** | "2026 你做了 87 次预测，Brier 0.19，胜过 78% 用户" | `Prediction` 表 + 战绩数据 | **低** | ⭐⭐⭐⭐ |
| **8** | **元预测** | 不预测事件，预测"人群会预测多少" | arena 已有 `probability` 人群值 | 低 | ⭐⭐⭐ |
| **9** | **1v1 对决** | 两人下相反预测，只有一方能赢 | 需新增房间机制 | 中 | ⭐⭐⭐ |
| **10** | **赛季制** | 主题赛季 + 结算节奏 | `arena-score` cron 已有 | 低 | ⭐⭐⭐ |

### 三个我认为最值得先做的（理由）

**① 概率演化追踪 —— 因为它训练的是预测领域最核心的技能**

超级预测者与普通人的真正差距不是"猜得准"，而是**"愿不愿意随新信息更新信念"**。
让玩家对同一事件多次预测，画出概率随时间的演化曲线，是**唯一能直接测量和训练这种能力**的机制。
→ 这条曲线本身就是极好的可视化产品，且现有 `Prediction` 表加一个 `probability` 字段即可起步。

**② 嵌入式预测 —— 因为它同时解决"可玩性"和"更多样本"**

预测不应该只发生在你的网站上，应该发生在**用户已经在的地方**：
- 浏览器插件：选中网页任意一句话 → 右键 → "预测这件事" → 生成带校准证书的概率并封存，到期自动回来告诉你
- Discord Bot：群里随手开一个预测
- 这直接把"可玩性"和"数据样本"两个诉求一次性解决，而且**完全符合你说的"接入任何场景"**。

**③ 预测解剖 —— 因为它是别人抄不走的差异化**

Metaculus 和 Manifold 都只给分数，不给诊断。而你有 `causal-reasoning` + `reflection-engine`，能指出"你在哪一步走错了"。
→ 这把产品从"打分工具"变成"教练"，这也是我上一版强调的**错误归因**，但在这里它回归到它应有的位置：**不是游戏机制，而是让预测变得有学习价值**。

## 五、协议化深化：把你的例子做实

### 5.1 核心产品：**带校准证书的概率（Certified Probability）**

这是协议层唯一的、也是足够强的卖点。裸 LLM 只能给一个数字，**你能给一个带信用背书的数字**：

```jsonc
// POST /api/forecast
{ "question": "Will X happen before 2026-12-31?",
  "resolution_criteria": "...", "domain": "tech" }

// Response
{
  "probability": 0.34,
  "ci95": [0.22, 0.47],
  "calibration_certificate": {          // ← 裸 LLM 给不了这个
    "brier": 0.136, "ece": 0.06,
    "n_resolved": 847,
    "domain_brier": { "tech": 0.140, "politics": 0.095, "science": 0.220 }
  },
  "reasoning_hash": "sha256:...",        // 前瞻性封存，防事后叙事
  "registered_at": "2026-10-10T08:00:00Z",
  "forecast_id": "fc_xxx"                // 后续可回探结算
}
```

**为什么这能立住**：ForecastBench 数据证明，裸 LLM（61.9）< 公众中位数（62.5）< 超级预测者（67.6）< 带工具的多智能体（69.0）。
**你的引擎就是那个"让裸模型变准"的层。** 你卖的不是预测，是**校准**。

### 5.2 三个协议层形态

| 形态 | 说明 | 谁会用 |
|---|---|---|
| **MCP Server** | Agent 调用 `forecast()` / `resolve()` / `my_accuracy()` | AI Agent、工作流、自动化 |
| **Embeddable Widget** | 任何网页嵌入一个"预测卡"，读者可下预测，全部汇入同一记分板 | 博客、媒体、Newsletter |
| **Browser Extension** | 选中任意文本 → 预测它 | 普通读者（门槛最低） |

### 5.3 一个更有想象力的形态：**预测作为社交原语**

社交媒体上你只能点赞、转发、评论。**如果第三种原语是"预测"呢？**

> 看到一条新闻，你不转发，而是附上："我认为这事 6 个月内会发生，概率 70%。"
> 三个月后，这条预测自动结算，出现在你的时间线上。

这把"表态"从情绪性的（点赞）升级为**可验证的判断**。
→ 在 2026 年"假新闻 / 立场表演"疲劳的语境下，**"我愿意为我的判断留下可验证记录"本身就是一种身份信号**。

### 5.4 协议化的风险与对策

| 风险 | 对策 |
|---|---|
| 做成底层后失去直接用户接触 | **双轨**：协议层负责分发与数据，自有玩法界面负责品牌与社区。两者必须同时存在 |
| 被调用方"白嫖" | 反正不以盈利为目的 —— 但要求**回传结局**（`resolve` 回调），把调用变成样本来源 |
| 标准之争 | 开源 + 主动向 ForecastBench 提交 + 与 Manifold/Metaculus 互补而非竞争 |

## 六、可玩性与成瘾性：设计原则（含明确边界）

### 6.1 用「良性成瘾」四要素（基于自我决定理论：自主 / 胜任 / 归属）

| 要素 | 具体机制 |
|---|---|
| **胜任感** | 校准曲线可视化进步 —— 不是"分数涨了"，而是"我变准了"（这是有格调的爽感） |
| **好奇心缺口** | 结算时刻的自然不确定性（**真实的可变奖励**，比人工设计的更强） |
| **社交承诺** | 组队、对决、公开承诺 —— 承诺一旦公开，回访动机内生 |
| **叙事** | 年度回顾、预测图鉴、事件故事线 —— 人需要"我的预测史"这种叙事身份 |

### 6.2 明确禁用（写进产品宪法）

| 黑暗模式 | 为什么禁用 |
|---|---|
| 无限滚动 / 自动播放 | 与"精密、克制"的品牌调性冲突 |
| 虚假紧迫感 / 倒计时逼单 | Precision Over Hype 原则直接禁止 |
| FOMO 制造（"你的朋友刚刚…"） | 虚假社交证明 |
| 损失厌恶操纵（streak 断裂的惩罚） | streak 断裂**只重置不断崖**，惩罚要温和 |
| 付费墙阻断核心玩法 | 既然不以盈利为目的，就更没理由阻断 |

> **理由**：这三重理由都指向同一个结论 —— ① 项目原则是 Precision Over Hype；② 操纵性设计会污染校准数据（玩家为保 streak 而保守作答）；③ 你的目标用户是高智识人群，**他们能识别并鄙视黑暗模式**。

### 6.3 关于「更多数据样本」：四条管道

这是你明确提到的诉求，也是整个设计的目的所在。

| 管道 | 机制 | 特点 |
|---|---|---|
| 1. 自有玩法 | 用户主动预测 | 质量最高，量最小 |
| 2. **嵌入式预测** | 在别人的场景里预测 | **协议化的最大红利，量最大** |
| 3. **Agent 代跑** | 其他 Agent 通过 MCP 调用 | 全自动，可规模化 |
| 4. 自动结算 | Manifold / Metaculus / 历史事件 | 已有 |

> **传统预测产品只能开管道 1。协议化让你同时开 1/2/3。**
> **这就是你说的"盈利性降低后空间更大"的具体兑现** —— 因为不用考虑计费，才能把 API 完全开放给管道 2 和 3。

## 七、盈利约束解除后，真正打开的是什么

| 打开的空间 | 说明 |
|---|---|
| **可以免费开放 API** | 从"卖调用次数"变成"占据标准位" |
| **可以开源** | 基础设施的前提是信任，闭源做不成协议 |
| **可以接入别人生态而不怕被白嫖** | Metaculus / Manifold / Discord / Notion 全部变成盟友 |
| **可以做长周期的事** | 数据集、标准、学术引用 —— 3–5 年才有回报，盈利导向下不可能做 |
| **可以说不** | 不做博彩、不做付费墙、不做增长黑客 |
| **⭐ 最大的空间：定义标准** | **"带校准证书的概率"这个品类目前无人定义。谁定义它，谁就是默认选项。** |

> **当所有人都在做产品时，做协议是唯一能赢的路径。**
> 而现在恰恰是窗口期：ForecastBench 证明了"校准"的价值，但还没有人把它做成可调用的能力。
